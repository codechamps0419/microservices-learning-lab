DATA OWNERSHIP RULES:
---------------------
  Service              Owns           Rule
  -------------------  -------------  ------------------------------------------
  product-service      product_db     No other service reads or writes it
  inventory-service    inventory_db   No other service reads or writes it
  order-service        order_db       Stores productId + productName snapshot.
                                      Never imports Product entity.
                                      Never accesses InventoryRepository.
  api-gateway           no database    Routes traffic and handles cross-cutting
                                      infrastructure concerns only.


ARCHITECTURE RULES:
-------------------
   1. API Gateway is the external entry point on port 8080.
   2. Product Service owns product_db exclusively.
   3. Inventory Service owns inventory_db exclusively.
   4. Order Service owns order_db exclusively.
   5. API Gateway owns no database.
   6. No service may access another service's database.
   7. Order Service stores productId, productName and unitPrice snapshots.
   8. Order Service must not store or import the Product entity.
   9. Order Service must not access InventoryRepository.
  10. External clients call business APIs through API Gateway.
  11. Internal service-to-service calls remain direct REST calls.
  12. Keep optimistic locking in Inventory Service using @Version.
  13. API Gateway must not contain Product, Inventory or Order business logic.
  14. API Gateway must not use JPA, Flyway, JDBC or blocking RestClient calls.
  15. Retry, circuit breaker, Kafka, Eureka, Redis, Saga frameworks,
      authentication and Docker remain outside this focused project.


WHY INTERNAL CALLS DO NOT ROUTE BACK THROUGH THE GATEWAY:
---------------------------------------------------------

  order-service directly calls product-service and inventory-service because
  the Gateway is intended as the external client boundary.

  Routing every internal call through the Gateway would:

  - Add an unnecessary network hop.
  - Increase latency.
  - Create additional coupling to the Gateway.
  - Make the Gateway a larger internal failure point.
  - Mix north-south traffic with service-to-service east-west traffic.

  For this project:

    External traffic:
      Client -> API Gateway -> Service

    Internal traffic:
      order-service -> product-service
      order-service -> inventory-service

4. DATABASE TABLE — order_db
--------------------------------------------------------------------------------

  order_db — table: orders
  +------------------+---------------+---------------------------------------+
  | Column           | Type          | Constraint / Notes                    |
  +------------------+---------------+---------------------------------------+
  | id               | UUID          | PRIMARY KEY                           |
  | product_id       | UUID          | NOT NULL — reference by ID only       |
  |                  |               | NO foreign key to product_db          |
  | product_name     | VARCHAR(255)  | NOT NULL — snapshot at order time     |
  | quantity         | INTEGER       | NOT NULL, CHECK > 0                   |
  | unit_price       | NUMERIC(10,2) | NOT NULL — snapshot at order time     |
  | total_price      | NUMERIC(12,2) | NOT NULL                              |
  | status           | VARCHAR(20)   | NOT NULL, DEFAULT 'PENDING'           |
  |                  |               | CHECK IN ('PENDING','CONFIRMED',      |
  |                  |               |           'REJECTED')                 |
  | correlation_id   | VARCHAR(100)  | nullable — for traceability           |
  | created_at       | TIMESTAMP     | NOT NULL                              |
  | updated_at       | TIMESTAMP     | NOT NULL                              |
  +------------------+---------------+---------------------------------------+

  KEY DESIGN DECISIONS:
  - product_id has NO foreign key to product_db. Services are independent.
  - product_name is a snapshot — captures the name at order time.
    If the product is renamed later, the order history stays correct.
  - unit_price is a snapshot — captures the price at order time.
    If the price changes later, the order total is still accurate.
  - No @Version on Order — orders are not concurrently updated after creation.
  - total_price uses NUMERIC(12,2) — two digits wider than unit_price to
    accommodate large order totals (quantity x price).
  - status defaults to PENDING — orders start as PENDING and move to
    CONFIRMED or REJECTED after downstream validation completes.
  - updated_at is included — status transitions (PENDING -> CONFIRMED/REJECTED)
    update this column via @PreUpdate.

6. SEQUENCE FLOW
--------------------------------------------------------------------------------

  Client
    |
    |  POST /api/orders  { productId, quantity }
    |  Header: X-Correlation-ID: <id>  (optional)
    v
  CorrelationIdFilter
    |  Read X-Correlation-ID header. If absent, generate UUID.
    |  Store in MDC. Forward on all outgoing calls.
    v
  OrderController
    |  @Valid — rejects missing productId, quantity < 1
    v
  OrderService
    |
    +-- Step 1: ProductClient.getProduct(productId)
    |           GET http://localhost:8081/api/products/{productId}
    |           <- ProductClientResponse { id, name, price, status }
    |           if 404 -> RemoteServiceException -> 404
    |           if timeout -> RemoteServiceException -> 503
    |
    +-- Step 2: Validate product.status == ACTIVE
    |           if INACTIVE -> ProductNotActiveException -> 422
    |
    +-- Step 3: InventoryClient.reserveStock(productId, quantity)
    |           POST http://localhost:8082/api/inventories/{productId}/reserve
    |           <- StockClientResponse { availableQuantity, reservedQuantity }
    |           if 404 -> RemoteServiceException -> 422 (no inventory record)
    |           if 422 -> RemoteServiceException -> 422 (insufficient stock)
    |           if 409 -> RemoteServiceException -> 409 (concurrent conflict)
    |           if timeout -> RemoteServiceException -> 503
    |
    +-- Step 4: Calculate totalPrice = product.price x quantity
    |
    +-- Step 5: Build Order entity and save to order_db
    |           stores: productId, productName (snapshot), quantity,
    |                   unitPrice (snapshot), totalPrice, status=CONFIRMED
    |
    +-- Step 5a (compensation — only if Step 5 fails):
    |           InventoryClient.releaseStock(productId, quantity)
    |           POST http://localhost:8082/api/inventories/{productId}/release
    |           Stock was reserved but order could not be saved — release it back.
    |
    +-- Step 6: Return OrderResponse -> 201 Created

7. ERROR MAPPING STRATEGY
--------------------------------------------------------------------------------

  Scenario                      Downstream response        order-service returns
  ----------------------------  -------------------------  ---------------------
  Product not found             product-service 404        404 Not Found
  Product is INACTIVE           (detected locally)         422 Unprocessable Entity
  No inventory record           inventory-service 404      422 Unprocessable Entity
  Insufficient stock            inventory-service 422      422 Unprocessable Entity
  Concurrent stock conflict     inventory-service 409      409 Conflict
  product-service is down       connection timeout         503 Service Unavailable
  inventory-service is down     connection timeout         503 Service Unavailable
  Request validation fails      (local @Valid)             400 Bad Request
  Order not found               (local)                    404 Not Found
  Order save fails              (local DB error)           500 + compensation triggered

  KEY PRINCIPLE:
  order-service's GlobalExceptionHandler catches RemoteServiceException and maps
  it to the appropriate HTTP status. The error message is translated into
  order-service's own language — never leaking internal service names or stack
  traces to the client.

8. CORRELATION ID FLOW
--------------------------------------------------------------------------------

  A correlation ID is a unique identifier attached to every request so you can
  trace it across all three services in the logs.

  Client sends:
    POST /api/orders
    Header: X-Correlation-ID: my-client-id-123   <- optional, client may send it

  CorrelationIdFilter in order-service:
    1. Read X-Correlation-ID header from incoming request
    2. If absent -> generate a new UUID
    3. Store in MDC (Mapped Diagnostic Context) — available in all log lines
    4. Forward the same ID in all outgoing RestClient calls as X-Correlation-ID

  ProductClient outgoing call:
    GET http://localhost:8081/api/products/{id}
    Header: X-Correlation-ID: my-client-id-123   <- forwarded

  InventoryClient outgoing call:
    POST http://localhost:8082/api/inventories/{id}/reserve
    Header: X-Correlation-ID: my-client-id-123   <- forwarded

  order-service response:
    Header: X-Correlation-ID: my-client-id-123   <- echoed back
    Body: { ..., "correlationId": "my-client-id-123" }  <- also in body

  WHY THIS MATTERS:
  When something goes wrong, you search all three service logs for the same
  correlation ID and see the exact chain of calls that led to the failure —
  without guessing.

  IMPLEMENTATION:
  CorrelationIdFilter implements OncePerRequestFilter.
  Uses MDC.put("correlationId", id) so every log line automatically includes
  the ID when the log pattern includes %X{correlationId}.

10. API GATEWAY MODULE — CURRENT FINAL ADDITION
--------------------------------------------------------------------------------

  The existing synchronous service flow remains unchanged internally:

    order-service -> product-service
    order-service -> inventory-service

  The api-gateway module is added as the external entry point:

    Client -> api-gateway (:8080) -> product-service   (:8081)
                                 -> inventory-service (:8082)
                                 -> order-service     (:8083)

  Gateway responsibilities:
  -------------------------
  - Route /api/products/**  to product-service.
  - Route /api/inventory/** to inventory-service.
  - Route /api/orders/**    to order-service.
  - Generate or preserve X-Correlation-ID.
  - Forward the correlation ID downstream and return it in the response.
  - Log method, path, status, duration and correlation ID.
  - Apply CORS for configured browser origins.
  - Apply the learning rate limit only to POST /api/orders.
  - Return standard 503 and 504 responses for Gateway-level failures.
  - Expose health and route information through Actuator.

  Gateway must NOT:
  -----------------
  - Access PostgreSQL.
  - use JPA, Flyway or repositories.
  - import Product, Inventory or Order entities.
  - calculate totals, validate product status or reserve stock.
  - replace business validation performed by downstream services.
  - use blocking calls such as RestClient, JDBC, Thread.sleep() or .block()
    in the reactive request path.

  Current Gateway dependency:
  ---------------------------

    org.springframework.cloud:
    spring-cloud-starter-gateway-server-webflux

  Deprecated dependency removed:

    spring-cloud-starter-gateway

  Current Gateway property prefix:
  --------------------------------

    spring.cloud.gateway.server.webflux

  Older keys such as the following are not used:

    spring.cloud.gateway.routes
    spring.cloud.gateway.httpclient
    spring.cloud.gateway.globalcors
    management.endpoint.gateway.enabled

  Current Actuator configuration uses:

    management.endpoint.gateway.access: read-only

  Gateway URLs:
  -------------

    Health:
      GET http://localhost:8080/actuator/health

    Registered routes:
      GET http://localhost:8080/actuator/gateway/routes

    Product through Gateway:
      GET http://localhost:8080/api/products/{productId}

    Inventory through Gateway:

  CORS preflight meaning:
  -----------------------
  Before a browser sends certain cross-origin requests, it sends an OPTIONS
  request asking whether the origin, HTTP method and headers are allowed.
  The Postman CORS request simulates that browser check. Postman itself does
  not enforce browser CORS restrictions.

  Rate-limit test:
  ----------------
  Run POST /api/orders more than the configured limit within the configured
  window. The default demonstration rule is 10 requests per 60 seconds per
  client IP. Requests beyond the limit should return HTTP 429.

11. WHAT YOU LEARN FROM EVERY PHASE
--------------------------------------------------------------------------------

  Phase 1 — Snapshot Data Ownership and Local Transaction Boundary
  -----------------------------------------------------------------
  Storing productName and unitPrice in order_db is not a boundary violation —
  it is deliberate denormalization. These are facts of the transaction at that
  moment. If the product is renamed or repriced later, the order history stays
  correct. This is the difference between a live reference and a historical record.

  The @Transactional annotation on OrderService methods wraps only order_db
  operations. The stock reservation in inventory_db is a completely separate
  transaction. There is no distributed transaction. This is the fundamental
  constraint of microservices: local atomicity within each service, eventual
  consistency across services.

  Order entity stores productId as a plain UUID — no @ManyToOne, no foreign key,
  no import of the Product class. Cross-service references use IDs only.

  Phase 2 — Client DTOs vs Shared DTOs
  --------------------------------------
  order-service defines its own ProductClientResponse and StockClientResponse
  instead of importing DTOs from product-service or inventory-service.
  order-service depends only on the HTTP contract (JSON shape), not on compiled
  code from other services. If product-service adds a field, order-service is
  unaffected. This is the correct way to consume another service's API.
  Importing another service's DTO creates compile-time coupling — the services
  can no longer be built and deployed independently.

  Phase 3 — RestClient and Timeouts
  -----------------------------------
  Connection timeout: protects against a service that is completely unreachable.
  Read timeout: protects against a service that accepts the connection but never
  responds. Without timeouts, one slow downstream service can exhaust all threads
  in order-service. Spring Boot 3.2+ RestClient is the modern replacement for
  RestTemplate. It is fluent, synchronous, and does not require extra dependencies.

  Phase 4 — Orchestration, Compensation, and Correlation ID
  -----------------------------------------------------------
  order-service is the orchestrator — it calls two downstream services in
  sequence and makes decisions based on their responses. Basic compensation
  (release stock on save failure) is the simplest form of distributed error
  recovery. It is not a full Saga — it only compensates the last step. The
  order of operations matters: always validate the product before reserving
  stock. Never reserve stock for an inactive product.

  MDC (Mapped Diagnostic Context) is a thread-local map that SLF4J uses to
  attach context to every log line. It is the standard way to propagate
  per-request data (like a correlation ID) through a service without polluting
  every method signature with an extra parameter.

  order-service must never leak internal service names, stack traces, or raw
  downstream error messages to its callers. GlobalExceptionHandler translates
  every exception into order-service's own error language. The correlationId
  is read from MDC inside the exception handler and included in every error
  response so the caller can trace the failure.

  Documentation generated from code annotations stays in sync with the
  implementation. Swagger UI lets you test endpoints directly from the browser.

  Phase 5 — Observability Basics (Postman / Manual)
  ---------------------------------------------------
  Correlation IDs are the simplest form of distributed tracing. When something
  goes wrong, search all three service logs for the same correlation ID and see
  the exact chain of calls that led to the failure. This is the manual version
  of what Zipkin and Jaeger automate. Understanding the manual version first
  makes the automated tools much easier to understand.

12. KEY DESIGN DECISIONS FOR INTERVIEWS
--------------------------------------------------------------------------------

  Q: Why does order-service store productName?
  A: Because at order time, the name and price are facts of that transaction.
     If the product is renamed later, the order history must still show what
     the customer ordered. This is intentional denormalization — a snapshot,
     not a live reference.

  Q: Why does order-service not import ProductResponse from product-service?
  A: Because that would create a compile-time dependency between two services.
     If product-service changes its DTO, order-service would fail to compile.
     Client DTOs (ProductClientResponse) depend only on the JSON contract,
     not on compiled code.

  Q: Why release stock when order save fails?
  A: Because stock was already reserved in inventory-service (a separate
     transaction in a separate database). If order-service's database write
     fails, the reservation is orphaned — stock is held but no order exists.
     Releasing it returns the stock to available. This is a compensating
     transaction.

  Q: Why is this not a full Saga?
  A: A full Saga would also compensate the product-service call. In this
     project, the product-service call is read-only (GET), so there is nothing
     to compensate. Only the inventory reservation needs compensation.
     A full Saga also requires Kafka/RabbitMQ or an orchestrator framework —
     out of scope for the synchronous-communication project.

  Q: Why can't @Qualifier be used on a Lombok @RequiredArgsConstructor field?
  A: Lombok generates the constructor from field declarations. Spring's
     @Qualifier annotation on a field is not transferred to the generated
     constructor parameter by Lombok. Spring therefore cannot distinguish
     which RestClient bean to inject. Fix: replace with an explicit constructor
     and put @Qualifier on the constructor parameter directly.

  Q: Why does WireMock conflict with MockMvc static imports?
  A: WireMock.* exports a post() method for stubbing. MockMvcRequestBuilders
     also exports a post() method for building requests. When both are statically
     imported, the compiler cannot resolve which post() to call. Fix: remove
     the MockMvcRequestBuilders static import and use the fully qualified
     MockMvcRequestBuilders.post(...) call instead.

  Q: What happens if the release call also fails?
  A: The stock remains reserved with no corresponding order — a data
     inconsistency. In production, this is handled by a background
     reconciliation job or a Saga framework. This project acknowledges
     the gap without solving it, which is the correct scope for a
     learning project.

  Q: What is the difference between connection timeout and read timeout?
  A: Connection timeout fires when the TCP connection cannot be established
     (server is down or unreachable). Read timeout fires when the connection
     is established but the server does not send a response within the
     configured time (server is slow or hung). Both must be configured.
     Without them, a single slow downstream service can block all threads.

  Q: What is MDC and why is it used for correlation IDs?
  A: MDC (Mapped Diagnostic Context) is a thread-local map provided by SLF4J.
     Values stored in MDC are automatically included in every log line when
     the log pattern references them (%X{correlationId}). It is the standard
     way to attach per-request context to logs without passing it as a method
     parameter through every layer of the application.

  Q: Why translate downstream errors instead of forwarding them?
  A: Forwarding raw downstream errors leaks internal architecture details to
     the client — they would see "inventory-service returned 422" instead of
     a meaningful business message. Translation also decouples the client from
     the internal service topology. If inventory-service is replaced by a
     different service, the error messages to the client stay the same.
